# Agent Note: 桌面媒体导入准入

Status: proposed

[English](2026-09-20-media-import-admission.md) | 中文

## Problem

会话内制作需要选取音频和视频文件，但当前命令附件信封只接纳图片。若把本地路径或媒体标识伪装成图片附件，就会绕过类型、归属和文件准入规则。第一版只需要为媒体工具选取文件，若此时修改通用聊天附件，则还会影响模型输入和两套 SDK。

## Proposal

desktop-media 插件将提供独立导入面板和受控上传路由。用户选取文件后，Host 才接收它，并执行可配置的字节数和时长限制、文件字节与 ffprobe 媒体流检查；随后复制到受管理目录，原子提交一条持久记录，生成带 `audio` 或 `video` 判别字段的不透明引用。被拒绝或中断的导入不能暴露可用引用。Client 针对类型不支持、大小或时长超限、流损坏及复制失败展示可操作的错误。客户端上传传输必须有界并经过实测，不采用整文件 Base64 RPC。

媒体工具只接收属于本会话和工作区、已经登记且由用户选用的引用。Host 从记录解析受管理文件的真实路径，并在读取或上传字节前检查归属；模型提交的路径、URL 和未登记标识一律失败。模型只看到已记录的导入结果与不透明标识，不接收本地字节或签名 URL。该规则只适用于新媒体工具，不改变现有 `read_image` 权限。

[图片附件决策](../../implemented/feature/2026-08-26-generic-file-upload.zh.md)明确规定：出现第二种受支持的附件类型时，命令信封应扩展为带标签的联合类型。第一版媒体导入是供媒体工具使用的插件记录，不是命令信封附件或通用模型输入，因此不满足该条件。以后若聊天直接接收音频或视频附件，必须同时扩展带标签联合类型，并更新准入、存储、命令信封校验、模型投影和两套 SDK 预期输出。

## Alternatives considered

**把音视频复用为图片附件。** 图片引用会错误暗示其遵循图片准入和模型可见语义，也会让按类型限制和访问检查含糊不清。

**第一版就扩展命令信封。** 第一版没有将音视频作为通用聊天附件发送的用户路径；此举会扩大命令、投影和 SDK 范围，却没有对应消费方。

**直接将本地路径交给工具。** 模型给出的路径没有选取记录或会话／工作区归属，可指向无关文件。

## Acceptance criteria

- 合法文件经过有界传输、类型与媒体流校验、原子文件提交后，才生成一条持久不透明引用；中断不留下可用引用。
- 测试须在提供方上传前拒绝伪装类型、无效媒体流、超大或超长文件、跨会话引用和模型提交的路径。
- 第一版不修改命令附件信封和图片 prompt 联合类型；模型可见导入结果可从会话日志重建。

## Risks

浏览器到 Host 的上传可能需要新的有界流式传输，并须在安装版验证。ffprobe 的结果不能保证外部播放器支持所有编码。以后加入聊天附件时，仍须实施上文所述的完整带标签联合类型变更。
