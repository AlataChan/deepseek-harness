# Agent Note: fork 自有文档从双语配对语料库中排除

Status: implemented

[English](2026-10-06-fork-owned-doc-exclusions.md) | 中文

## Problem

`verify-translation-pairing` 要求范围内每篇文档都以完整的英中配对合并。本 fork 携带了一些既没有可配对对侧、也没有需要中文的读者的文档：Tauri 外壳的 README 与图标说明、companion carrier 包、随附 Python sidecar 的目录说明，以及读者是评审该工作的 owner 的带日期过程性方案。

这些文档未通过门禁，而**合并上游**正是它从"外观问题"变成"阻塞问题"的地方。合并提交会暂存整棵树，因此每个未配对的 fork 文档会一次性被检查；由于提交被钩子把关，在清偿这笔欠账之前，本 fork 根本无法合并上游。本决定之前已有十份此类文档。

## Decision

**把它们作为显式排除项列入 `scripts/translation-pairing.manifest.json`，并在 `docs/i18n/README.md` 中说明每一组的理由。** 该 manifest 本就是为此而存在，且门禁已经会拒绝为被排除路径建立 `.zh.md` 或 `.i18n.yaml`，所以排除是一个封闭陈述，而非放松约束：译者事后无法为一个被排除路径补一份半维护的对侧。

**三组，每组一条理由。**

- 本 fork 自有的桌面与 companion 面——外壳、其图标，以及 companion carrier 包。上游没有可配对的对侧；其读者是本 fork 自己的维护者，而不是已发布产品的读者。
- 带日期的过程性方案——读者是评审该工作的 owner，且工作落地后方案是被取代而非被维护。方案若被提升进 `docs/` 正式文档，则以其新路径加入语料库。
- 随附 Python sidecar 的内部说明——sidecar 的 prompt 与 schema 目录树说明，读者是编辑这两棵树的人。

**不为 `docs/plans/` 加目录级条目。** 该目录下已有两个方案带经评审的中文对侧，而排除目录会让门禁把这两个既有配对当作"不得存在的翻译"而拒绝。四份未配对方案逐条列名，这也意味着今后的方案要么带上配对，要么在此处被刻意加入。

## Consequences

- 配对门禁通过，因此上游合并可以被提交。范围内其余 fork 文档要么已配对，要么已在 manifest 中列名。
- 新增的 fork 自有单语言文档现在会失败，直到它被配对、或被连同理由加入 manifest。这是预期的代价：该决定保持刻意作出，而不是反复以无法解释的红灯出现。
- 被排除路径不得携带 `.zh.md` 与 `.i18n.yaml`。日后补对侧必须在同一次改动中移除排除项，因此两种状态不可能同时成立。
- 这些排除项是本 fork 自己的，不是上游的。上游合并若改写其中某个路径，会带来冲突，而不会静默地取消排除。
- 这些文档仍然存在于仓库中并保持可读；改变的只是它们参与配对契约的关系。

## Alternatives considered

- **翻译全部十一份文档。** 不采纳：配对契约是为已发布产品的读者而存在，而这些文档没有这样的读者。翻译一份带日期的方案还会产出第二份需要与"反正会被取代的工作"保持同步的文档。
- **把 `docs/plans/` 整体作为目录排除。** 不采纳：该目录下已有两个配对，排除目录会让门禁把那些配对当作禁止的翻译而拒绝。
- **把门禁收窄为跳过未配对的 README。** 不采纳：那会静默豁免整个产品面，而不是点名这五个 fork 自有的 README，而 README 配对正是该契约的用途所在。
- **绕过钩子提交合并，事后修文档。** 不采纳：那会让引入该改动的提交本身带着红灯，而这正是仓库门禁规则要防止的状态。
- **把十一份文档逐个手工带过来。** 这是两个生成 catalog 所走的路径——它们是配对文档，必须随其英文源一起移动。在这里它是错误的工具，因为这里不想要的正是配对本身。
