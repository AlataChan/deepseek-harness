# Agent Note: 知识库上传把多份文件排进同一个库

Status: implemented

[English](2026-09-16-knowledge-batch-upload.md) | 中文

## Problem

知识库一次只能收一份文档，手上五份材料就得重复上传五遍、看五次各自的 180 秒等待。报告读起来像是缺一个批处理或排序步骤。

它由三个独立的限制造成。选文件控件没有 `multiple`，所以系统对话框只能交回一个文件，而选择器读的是 `el.files?.[0]`。`finishIngestPipeline` 跑在 `withLibraryLock(libraryId, …)` 里 —— 一把按 libraryId 分键的进程内互斥 —— 所以同一个库的两份入库无法重叠，第二份要等第一份；这种串行是刻意的，因为这条链在写 vault，而冻结的 sidecar `validate-apply` 不是并发安全的。而 `session/finishAskKnowledgeIngest` 是唯一带超额 carrier 预算（180 秒）的方法，因为一次调用要跑 recover、`ingest-file`、一次 LLM `propose` 和 apply —— 预算按次，所以 N 份要付 N 个串行预算。

报告者想要的「排序」其实早就存在：就是那把库锁。缺的是一个队列。

## Decision

选择器改为一次收多份文件，并在客户端逐份入库到同一个库。input 加上 `multiple`，`deliver` 交出整个 `FileList`，`ingestBatch` 顺序遍历它，每份 await 完 `finishIngest` 再起下一份。整批留在同一个库：第一份经既有的 `ensureDraft` 缓存建出草稿库，其余都并进它。

每份文件拥有自己的一行，在「排队中 / 正在处理 / 已入库 / 失败原因」之间移动，所以长批次显示的是进度而不是一次全局等待。某份失败不会中断整批：`ingestOne` 返回自己的原因而不是写选择器的共享 error，驱动记下它并继续；抛出的传输错误也按文件捕获，理由相同。只有当至少一份落地时，选择器才挂库并关闭；整批全失败则保持打开，每条原因都可见。

不支持的扩展名筛选留在驱动里、在任何户口本写入之前，这样 Host 本来会拒的文件不会留下一个空库。唯一给库命名的是**第一份成功**的文件，且只在该行仍未命名时，所以五份的批次只命名一次。

「顺序」是整个设计，不是初版权宜。库锁本来就会把并发入库串行化，真正的成本是每份一次 LLM `propose`，而并发只会给一个用户看不见的步骤加更多失败模式。

## Alternatives considered

**单独写一个文档处理或排序脚本。** 否决：它会重复 convert → propose → apply 这条链并与之漂移，还得把单写者锁重造一遍；它也拿不到 Host 为 `propose` 掌管的凭据注入，并且绕过 carrier 预算和选择器的逐份失败面。

**同一个库内并发上传。** 否决：`withLibraryLock` 无论如何都会串行化它们，唯一效果是更多在途失败和被限流的 `propose`。

**跨不同库并发上传。** 否决：用户是把几份文档归进一个库；把一批摊到多个库是另一个功能，且需要每份文件各自的落点。

**做能扛住关窗口的持久队列。** 暂缓：那需要新的会话事件、进度投影和一个作业所有者，比报告的缺陷大得多。浏览器里的队列明确记录为「没轮到的会丢」。

**像以前那样把失败都放进选择器的共享错误行。** 否决：一行说不清五份里是哪份失败。逐份行带上原因；两个原先读共享行的既有测试改读该行。

## Consequences

一次动作现在能归档多份文档，而且用户能离开：批次逐份自报，并在至少一份落地时以挂库一次收尾。五份的批次仍然要约五段串行入库等待，进度行让它可见，而不是藏起来。

关掉窗口会丢掉队列还没轮到的那几份；它们没有被记录在任何地方，用户需要重新选。一份失败会留下已成功的那几份，这正是部分批次应有的含义。

`BatchEntry`、`BatchState`、`shouldNameFromStem`、`updateBatchEntry`、`batchEntryText` 都留在模块内：测试驱动选择器，选择器的 `/client` 面不变。`batchEntryText` 里有一个不可达分支 —— 驱动写每条失败条目时都带原因 —— 并带有说明这一点的 `v8 ignore`。验证见 `packages/experimental/desktop-ask-knowledge/tests/library-picker.client.spec.tsx`：多份文件进同一个库且只建一次、只改名一次；排队→处理中的过渡；返回型错误与抛出型错误的失败隔离；全失败时保持打开；以及文件列表为 null。
