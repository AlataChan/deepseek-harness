# Desktop Windows EXE Plan (DMG feature parity for Windows x64)

Mode: integrate

Space: desktop-windows-exe (branch `feature/desktop-windows-exe`)

Created: 2026-10-11

Revised: 2026-10-11 (Plan Review round 1: 6.5 FAIL — 4 blockers integrated. Round 2: 7.3 PASS — 4 residual fixes integrated)

Architect: Cla

## Goal

Produce a self-contained Windows x64 installer, `dist/octopus_DSH_Setup.exe` (NSIS), with the same user-visible feature set as the shipped macOS DMG: bundled Node runtime, bundled Harness + desktop companion, ask-data, ask-knowledge (frozen Python sidecar), agent team, files, skills, and the profile plugin pins. A new user installs the EXE and only enters an API Key.

Parity exception (owner decision, see Open Decisions): the `env-ngo-project-assistant` preset is copied from a path outside this repository on the owner's Mac, so CI cannot read it. The Windows build takes presets through an explicit `--presets` parameter and ships without them unless the preset is committed to the repository.

## Constraints that decide the design

1. Tauri has no supported macOS → Windows cross-compilation (needs MSVC, WebView2, NSIS), and PyInstaller cannot cross-compile the ask-knowledge sidecar. The build must run on Windows.
2. The fork repository is public, so GitHub-hosted `windows-2025` runners are free; this is the only path where the same agent builds and self-verifies the artifact.
3. The DMG pipeline is shipping and must not regress. `scripts/build-dmg.sh` and `scripts/verify-desktop-bundle.sh` stay behaviorally unchanged. `scripts/smoke-companion-lifecycle.mjs` gains platform-aware layout detection; the DMG gate keeps exercising its macOS path.
4. The crate in `apps/desktop/src-tauri` has never been compiled for Windows in this repository (no workflow builds or checks it; `apps/desktop/README.md` claims otherwise and is corrected by this work). The first Windows compile is a priced risk, so it runs before the expensive payload steps.

## Reusable surfaces (verified before planning)

- Rust shell is platform-neutral: `app.path().resource_dir()`, `node.exe` naming, `.cmd`/`.ps1` shim rejection in `apps/desktop/src-tauri/src/runtime.rs`.
- Resource layout contract: `resource_dir()/resources/{node.exe,harness/,profile-plugins/,bundled-skills/,presets/,kb-runtime/,installed-runtime-cli.js}`, identical to the macOS `Contents/Resources/resources/` tree. `app.rs` returns an empty resource set when a directory is absent, so `presets/` and `kb-runtime/` degrade instead of failing the boot.
- `packages/experimental/desktop-ask-knowledge/src/sidecar.ts` already probes `octopus-kb-sidecar.exe`.
- `scripts/seed-desktop-profile-plugin.mjs` is a Node script with no macOS-only logic; the data-agent pin is pure JS (no native modules). `scripts/collect-runtime-deps.mjs` is not Windows-clean today (see deliverable 4).
- Tauri `bundle.resources` supports an explicit source → target map, so the staged payload can live outside `apps/desktop/src-tauri/resources/` and still land at `resources/<name>`.
- `apps/desktop/src-tauri/icons/render.sh` already requires ImageMagick for the PNG/ICNS pair; the Windows `.ico` is one more `magick` line in the same script.

## Deliverables

1. `apps/desktop/src-tauri/tauri.windows.conf.json` — `targets: ["nsis"]`, `icon.ico`, and the resource map for the staged payload, which must keep carrying `resources/installed-runtime-cli.js` (platform config merges at the JSON level, so the base array entry can be replaced). `webviewInstallMode` stays unset: the default `downloadBootstrapper` matches the product's size sensitivity, and neither the runner image nor Windows 10 1903+/11 targets lack WebView2 in practice. Base `tauri.conf.json` (macOS) stays untouched.
2. `apps/desktop/src-tauri/icons/icon.ico` — generated by `render.sh` (`magick` multi-size `.ico`) and committed, because CI cannot run that script (`iconutil` is macOS-only); `icon.png` / `icon.icns` outputs stay unchanged.
3. `scripts/build-exe.mjs` — Windows build entry mirroring `build-dmg.sh` step for step: preflight (Tauri CLI, Rust toolchain, Python) → compile the `dsh-desktop` crate (fail fast, minutes) → download and SHA-256-verify `node-v24.14.0-win-x64.zip` against `SHASUMS256.txt` and extract with `tar -xf` (bsdtar ships in `System32` and reads zip; Node 24 has no built-in unzip) → `collect-runtime-deps.mjs` → seed profile plugins and bundled skills → freeze the KB sidecar (unless `--skip-kb`) → optionally stage presets (`--presets <dir>`; `none` is a printed warning, not an error) → stage the payload tree → bundle with `pnpm dlx @tauri-apps/cli@2.11.4 build --bundles nsis` (fallback `cargo install --locked tauri-cli@2.11.4`, cached) → copy the installer to `dist/octopus_DSH_Setup.exe`. Plain Node, no new dependencies. The compile step runs after `pnpm run build`, because `build.rs` regenerates `installed-runtime-cli.js` from the built package.
4. `scripts/collect-runtime-deps.mjs` — separator fix: `copyPackage` compares Node's `\`-separated paths against `/`-joined strings, so on Windows `SKIP_TOP_LEVEL` (`node_modules`, `tests`, `test`, `.turbo`, `coverage`) and workspace `src/` are never dropped and `dereference: true` copies nested store trees into the farm. Use `path.relative`/`path.sep`; the macOS output stays byte-identical.
5. `scripts/build-kb-sidecar.mjs` — platform-aware port of `scripts/build-kb-sidecar.sh` (venv layout, PyInstaller `--add-data` separator, `.exe` output, the same self-test expectations, pip and PyInstaller versions pinned). The `.sh` stays for macOS.
6. `scripts/verify-desktop-exe.mjs` — Windows readiness gate, mirroring the `.sh` gate where it applies: skeleton (`dsh-desktop.exe` + resource tree, resolving the binary by name and reporting which one it found), `node.exe --version`, harness manifest, companion module-graph smoke, pinned-overlay lifecycle smoke, no symlinks, no build-machine paths that escape the install, plugins/skills present, KB sidecar `self-test` (`ok`, `pdf`/`xlsx`, `proposalSchema`/`applyRules`/`rulesSchema`/`pageMetaFill`/`retrieveFold`/ `convertFile`, and the `magika` model file), plus the relocatability check (copy `kb-runtime`, re-run `self-test`). Preset checks run only when the build declared a preset source; `--skip-kb` selects the documented slim mode whose pass criteria exclude both the sidecar checks and the ask-knowledge pin in the lifecycle smoke. It runs against the **installed** tree.
7. `scripts/verify-desktop-exe.spec.ts` (or an equivalent `.spec.ts` beside the scripts) — one guard that parses `build-dmg.sh` / `build-kb-sidecar.sh` and asserts the duplicated constants still match the `.mjs` builds: `NODE_VERSION`, the eight self-test keys, and the PyInstaller flag set (`--collect-all` / `--hidden-import`). Pip and PyInstaller versions are pinned in the `.mjs` only, so the comparison excludes them. `.oxlintrc.json` ignores `**/*.mjs`, so this spec is the enforcement for those files.
8. `.github/workflows/desktop-windows.yml` — `workflow_dispatch` (plus a temporary `push` trigger on the feature branch, removed before merge): `windows-2025`, `timeout-minutes: 60`, `permissions: contents: read`, `concurrency: { group: '${{ github.workflow }}-${{ github.ref }}', cancel-in-progress: true }`, checkout with `persist-credentials: false`, pnpm setup with the native Windows `dest` (`${{ runner.temp }}/setup-pnpm-js-<run>-<attempt>-<job>`), Node 24, Rust stable, Python 3.12, `DSH_TELEMETRY_DISABLED: '1'`, the Developer-Mode symlink step the Windows lanes run, the ReFS install branch (`$fs -eq 'ReFS'` → `pnpm install --frozen-lockfile --package-import-method=clone`, copied verbatim from `ci.yml`), and caches for the pnpm store, cargo registry, and `src-tauri/target`. Steps: `pnpm install` → `pnpm run build` → `node scripts/build-exe.mjs` → silent install (`octopus_DSH_Setup.exe /S /D=<runner.temp>\octopus_DSH`, `/D` last and unquoted) → `node scripts/verify-desktop-exe.mjs <install-dir>` → artifact upload.
9. `scripts/smoke-companion-lifecycle.mjs` — minimal edit: detect bundle layout (`*.app` vs directory root), resolve the Node binary name per platform, and use `os.homedir()` + `path.isAbsolute` instead of the `HOME`/leading-slash test. macOS behavior unchanged.
10. `.github/AGENTS.md` — one policy sentence placing `desktop-windows.yml`: manual dispatch, release-adjacent, not part of the PR check panel. One Agent Note (with its `.zh.md` counterpart, per the translation-pairing gates) records the durable decision (Windows builds are CI-only because neither Tauri nor PyInstaller cross-compiles from macOS). `apps/desktop/README.md` line 18 is corrected: the crate is not compiled on Windows in this repository's CI; `desktop-windows.yml` is the first Windows compile.

## Sequencing

- Phase A: branch `feature/desktop-windows-exe`; deliverables 1–9; run `render.sh` locally for the `.ico`; re-run `scripts/verify-desktop-bundle.sh` against the existing `.app` to prove deliverable 8 did not regress the DMG gate.
- Phase B: push, run the workflow, iterate to green. Expected 2–5 CI runs; each iteration fixes exactly one failing gate and reruns the affected branch of the pipeline.
- Phase C: the readiness gate is a hard gate before artifact upload; no green gate, no artifact.
- Phase D: hand over the artifact link (optionally a tagged GitHub Release on request). Owner acceptance on a real Windows machine: install → API key → first conversation.

## Verification

- Local: `pnpm run test` for the new spec and any touched repository files; `scripts/verify-desktop-bundle.sh` against the current `.app` for the smoke-script edit.
- CI: install → readiness gate → artifact. The workflow itself is the packaging gate.
- Note for reviewers: `pnpm run lint` does not inspect `**/*.mjs`; the spec plus the CI gate are the enforcement for the new build scripts.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| `cargo tauri` is absent on the runner (`tauri-cli` is a cargo-installed tool, no npm pin in the repo) | `pnpm dlx @tauri-apps/cli@2.11.4` with a cached `cargo install --locked` fallback; `build-exe.mjs` preflight fails with that sentence instead of a raw cargo error |
| First Windows compile of the Tauri crate (never compiled in this repo) | compile step placed before payload assembly so a Rust error surfaces in ~2 minutes, before the harness farm and the PyInstaller freeze |
| `cargo tauri build` resource map syntax for directories | The schema documents map sources as absolute or `../relative` paths, so staging outside `src-tauri` is supported; the first CI run validates the installed layout, and the fallback is staging into `src-tauri/resources/` with the list form and `.gitignore` entries |
| PyInstaller freeze (magika/onnxruntime, markitdown) fails or is slow on Windows | isolated step; `--skip-kb` gate mode keeps a slim, verified EXE buildable while the freeze is fixed |
| `node-pty` / native addons during `collect-runtime-deps.mjs` on Windows | per-platform optional-binary resolution; the separator fix (deliverable 4) is what makes the farm content match macOS |
| WebView2 missing on the target machine | the default `downloadBootstrapper` mode fetches it at install time; `offlineInstaller` (+~127 MB) stays available if owner feedback shows offline machines in the field; GUI launch on the runner is a stretch check, not a gate |
| Unsigned installer triggers SmartScreen "Windows protected your PC" | same family as the macOS Gatekeeper note: document "更多信息 → 仍要运行"; code signing is out of scope |

## Out of scope

- Code signing / EV certificate, auto-update, Windows arm64, MSI target, Gitee mirror publication, changes to the macOS DMG pipeline.

## Open decisions (owner)

1. Presets: commit `env-ngo-project-assistant` into this (public) repository so both builds ship it, or ship the EXE without presets in v1.
2. Build path: this plan assumes the GitHub Actions route (the only path the same agent can run and self-verify). A local Windows machine build would need the owner to run the build and hold the verification burden.

## Rollback

All work is additive on `feature/desktop-windows-exe`; deleting the branch removes the Windows build without touching the DMG path.
