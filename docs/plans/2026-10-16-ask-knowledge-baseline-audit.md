Most of the archived independent controls pass: 13 of 13 round-1 Python controls, 9 of 9 round-2 Python controls, and 9 of 11 archived Host/Client controls. The upload approval gate, same-name import preservation, source indexing freshness, Unicode offset mapping, PDF mixed-content classification, symlink rejection and the full-response budget all reproduce as repaired.

The only accepted-looking failure is environmental, and it has a product-side co-cause. Every approved-extraction control fails because this host answers a child process's outbound HTTP to loopback with `403` and an empty body; the child's client then parses nothing at `python/kb/src/octopus_kb_compound/llm.py:63` and raises `Expecting value: line 1 column 1 (char 0)`. A control written for this audit reproduces the interception with no product code in the loop, and a diagnosis probe shows why the child is proxied at all: `src/sidecar.ts:231-237` gives the knowledge child no proxy environment at all, so Python falls back to the macOS system proxy and drops its loopback bypass, while every other harness child receives `NO_PROXY=localhost,127.0.0.1,::1,[::1]` through `packages/subprocess/subprocess-local/src/spawn.ts:44-46`. K3 and R2-7 are superseded by the audited tree, which already exposes continuation and a passage-read tool and discloses capped candidates. R2-9's private per-vault cursor key and its refusal of forged and cross-library continuations are now verified. Three Required controls that the round-2 review left unrerun (K5, K7, R2-6) now have executed evidence, and K7 and R2-6 close.

The 100 MiB upload ceiling must not be adopted yet. The plan names WebView memory and transport throughput as the deciding measurements. Transport throughput is now measured in Node (see Measurement A); WebView memory is not measurable outside the browser.

## Scope and method

This audit covers the ledger of K1–K15 and R2-1–R2-10, the three measurement families the plan requires, and a rerun of the archived independent controls. It does not repair product code and does not claim acceptance.

Disposition vocabulary is deliberately strict. `verified closed` means every control named for the finding and every remaining obligation from its round-2 row was exercised by a command in this run. `still open` means at least one named obligation has no executed evidence, with passing probes noted. `superseded` means the audited tree no longer contains the reported defect, with source and executed-control evidence. `environment-blocked` means a layer outside this repository intercepts the control in the default environment, so the obligation is recorded as observed only under an explicit bypass, or not at all. `unverified` means no executed evidence exists at all. A passing helper test or a remediation report never closes a finding; only a rerun of the named control or a measurement counts.

Commands were run from the repository root. Measurement scripts import production TypeScript by relative path under `node --import tsx/esm`, so they resolve workspace packages through the root `tsconfig.json` paths without a build. Python controls run under `/opt/homebrew/bin/python3`. No paid inference, network model call, `DEEPSEEK_API_KEY` use, DMG build, Windows workflow or whole-repository test run was performed.

## Measurement A: whole-file upload path

The current library upload reads the whole file into memory and encodes every chunk before the first remote call: `readFileBytes` at `packages/experimental/desktop-ask-knowledge/src/client/bytes.ts:25` calls `file.arrayBuffer()`, `LibraryPicker.tsx:245` passes the result to `encodeIngestChunks`, and `src/client/ingest-file.ts:80` slices it into 160 KiB base64 chunks. The same pattern appears at `src/client/extract-file.ts:39` for session-only documents.

`measure-upload-path.mts` replicates that path in one process and adds the Host admission step, `appendUpload` at `src/upload-temp.ts:168`, with the default cap `DEFAULT_MAX_INGEST_BYTES` (`src/upload-temp.ts:16`) and the configured cap at `src/index.ts:151`.

| Size | Client chunks | In-process `appendUpload` calls | Base64 chars | Inflation | `encodeIngestChunks` | Host admission | Peak RSS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 MiB | 7 | 7 | 1,398,120 | 1.3334 | 32 ms | 7 accepted | 113.2 MiB |
| 10 MiB | 64 | 64 | 13,981,184 | 1.3333 | 248 ms | 64 accepted | 172.0 MiB |
| 25 MiB | 160 | 160 | 34,952,960 | 1.3333 | 645 ms | rejected at chunk 128 | 316.5 MiB |
| 50 MiB | 320 | 320 | 69,905,920 | 1.3333 | 1,235 ms | rejected at chunk 128 | 541.9 MiB |
| 100 MiB | 640 | 640 | 139,811,840 | 1.3333 | 2,524 ms | rejected at chunk 128 | 808.8 MiB |

The chunk column is the client's chunk count, which is also the shipped path's count of remote append round trips. The `appendUpload` column is not remote: `measure-upload-path.mts` calls the Host function in-process to isolate admission cost and rejection ordering, while `measure-transport.mts` (`transport-measurements.log`) measures the real Client → `ProcessTransport` → `StdioLinePort` → `VsCodeIpcChannel` → `VsCodeHostGateway` → `DesktopAskKnowledge` transport and the official attachment upload routes. Under the default 20 MiB cap, `askKnowledge` desktop RPC accepts 1 MiB (`8` wire records each way, `1,400,453` wire bytes C→H, `64.9 ms` append, `16.86 MiB/s`, `155.4 MiB` peak RSS), 10 MiB (`65` records, `14,000,048` bytes, `531.3 ms`, `18.82 MiB/s`, `267.9 MiB` peak RSS), and 20 MiB (`129` records, `27,999,792` bytes, `942.1 ms`, `21.23 MiB/s`, `462.5 MiB` peak RSS), and rejects 25/50/100 MiB at chunk index `128` (`file exceeds 20971520 bytes`) after sending `130` wire records (`28,218,538` bytes C→H). With `maxIngestBytes` raised to 100 MiB to measure full transport capacity, 50 MiB completes in `10,003.8 ms` (`4,662.6 ms` read+encode + `5,334.2 ms` append across `321` wire records, `69,999,024` wire bytes C→H, `9.37 MiB/s`, `538.5 MiB` peak RSS, `+100 MiB` ΔRSS) and 100 MiB completes in `15,440.7 ms` (`8,700.3 ms` read+encode + `6,729.2 ms` append across `641` wire records, `139,997,745` wire bytes C→H, `14.86 MiB/s`, `561.0 MiB` peak RSS, `+200 MiB` ΔRSS). Mid-flight abort after 32 chunks of a 20 MiB upload leaves `<knowledgeHome>/tmp/<uuid>` on disk while the Host stays live (`remainingTmpDirsWhileLive: 1`, because no `abortIngest` RPC exists), and cold restart after an ungraceful crash leaves `<knowledgeHome>/tmp/<uuid>` uncleaned (`tmpDirsBeforeRestart: 1`, `tmpDirsAfterColdRestartInit: 1`). By contrast, official attachment HTTP streaming (`POST /api/upload/file` → `saveFileStreamVerbatim`) streams 1–100 MiB at `8.19–378.25 MiB/s` (`264.4 ms` and `+0.4 MiB` ΔRSS at 100 MiB) and removes its staging file immediately on mid-stream abort (`stagingFilesRemaining: 0`), whereas unary `fileUploads/upload` over `ProcessTransport` fragments 1–50 MiB into `10–358` wire records at `7.48–11.59 MiB/s` (`1,085.9 MiB` peak RSS at 50 MiB) because `ProcessTransport.fetch` rejects non-JSON request bodies (`desktop API request body must be JSON text`).

Three facts matter for Task 2. Peak RSS reaches 808.8 MiB for a 100 MiB file, about eight times the payload, because the decoded buffer, the slice views and the base64 strings coexist. The wire cost is exactly 4/3 of the file size, unmodified by chunking. The default 20 MiB admission cap, `file exceeds 20971520 bytes`, refuses a 25 MiB or larger upload only after 128 successful chunk calls, so a rejected 25 MiB upload has already made 128 of its 160 chunk calls.

**WebView is not measured and is explicitly not claimed.** These numbers come from a Node 24 process with `--expose-gc`. `file.arrayBuffer()`, the base64 encoder, the renderer's memory pressure and the Cordis remote transport behave differently in a WebView. The plan makes WebView peak memory and transport throughput the deciding measurements for the 100 MiB ceiling, so this table cannot decide that question.

The plan's statement that an accepted attachment can be retained while its conversion is explicitly refused is consistent with these measurements: storage is uncapped and content-addressed, while conversion and library admission each refuse above their own limits.

One consequence follows from the same measurements and constrains Task 2's retention design. Attachment storage accepts any size, keeps every original indefinitely and serves them across sessions by digest, and session-log export traverses each durable file block. Evicting an overlay cache therefore does not remove a document: the original stays under the attachments root and stays reachable through any exported session log that referenced it.

## Approved extraction: environmental interception with a product co-cause

Five test cases in four sources fail at the same point: the archived `production-controls.spec.ts` late-content case, `controls/approval-flow-controls.spec.ts` written for this audit, the producer's own `tests/upload-approval.spec.ts` late-content case, and two `tests/document-enrichment.spec.ts` cases. Four separate runs recorded the same failure: `controls-rerun.log`, `package-enrichment.log`, `package-suite-bounded.log` and `upload-approval-late-content-fail.log`.

The approval machinery itself works. In the approval-aware control, approval is accepted, the plan is written with `budgetApproved: true` and `approvedTokens: 130288`, a chunk checkpoint is written with `state: "calling"`, and the frozen route points at the fixture server. The fixture records zero provider requests, and the child answers with `Expecting value: line 1 column 1 (char 0)`.

That string is a JSON parse of an empty body, not a product decision. `python/kb/src/octopus_kb_compound/llm.py:63` returns `response.status_code, response.json()`, so an empty body raises exactly this. `src/sidecar.ts:127` only re-wraps the JSON error the child printed to stdout, which is why the stack trace stops there, and `KnowledgeProcessExitError` carries the child's `stderr` from `src/sidecar.ts:264` so a nonzero exit reports the child's own output.

`controls/child-network-control.mjs` isolates the cause with no product code in the loop. It binds a Node HTTP server on `127.0.0.1`, sends one request from the Node parent, then spawns a plain `/opt/homebrew/bin/python3` child that posts to the same server through httpx.

| Observation | Result |
| --- | --- |
| Parent Node `fetch` to the loopback fixture | `200`, body `{"ok":true,"path":"/parent"}` |
| Child python httpx POST with every proxy variable cleared | `403`, empty body, headers `connection: close`, `content-length: 0`, `cache-control: max-age=3600, public` |
| Child python httpx POST with the inherited environment | `ImportError: Using SOCKS proxy, but the 'socksio' package is not installed` |
| Paths the fixture server actually served | `["/parent"]`; the child's request never arrived |

The child's request is answered by a layer outside this repository. Both variants fail for environment reasons: the inherited environment routes the child through a SOCKS proxy that cannot be used, and the cleared environment is intercepted with a cached `403`. The parent process is unaffected, so the interception applies to a spawned child rather than to the loopback server.

The intercepting layer is outside this repository, and the product's knowledge-child environment is a co-cause. `src/sidecar.ts:231-237` builds that child's environment from process-wide tombstones plus a nine-name allowlist — `PATH`, `HOME`, `TMPDIR`, `TEMP`, `TMP`, `SystemRoot`, `SYSTEMROOT`, `WINDIR`, `LANG` — so the child receives no proxy variable at all, including no `NO_PROXY`/`no_proxy`. Every other harness child is given the opposite: `packages/subprocess/subprocess-local/src/spawn.ts:44-46` builds its environment through `scrubbedParentEnv()`, which keeps the proxy names and overlays the resolved bypass from `packages/util/http-proxy/src/install.ts:262-279`, and `packages/subprocess/subprocess/src/index.ts:66-80` is where that scrub and overlay run. The bypass is never optional: `packages/util/http-proxy/src/policy.ts:33` lists `LOOPBACK_NO_PROXY = ['localhost', '127.0.0.1', '::1', '[::1]']`, `policy.ts:206-211` merges those entries into every resolved policy, and `packages/subprocess/subprocess/tests/egress.spec.ts:137` asserts the resulting `NO_PROXY === 'localhost,127.0.0.1,::1,[::1]'` with the comment that without it a child sends its own localhost traffic to the proxy.

With no proxy variable, Python's `urllib.request.getproxies()` falls back to the macOS system configuration. `scutil --proxy` on this host reports `HTTPEnable 1` / `HTTPProxy 127.0.0.1` / `HTTPPort 7897` and `SOCKSEnable 1` / `SOCKSPort 7897`, with an `ExceptionsList` that contains `127.0.0.1` and `localhost`. That fallback returns the proxy addresses but not the exceptions: `/opt/homebrew/bin/python3` with every proxy variable unset prints `{"http": "http://127.0.0.1:7897", "https": "http://127.0.0.1:7897", "socks": "http://127.0.0.1:7897"}` and no bypass entry, while the same interpreter with the ambient variables present prints the extra `"no": "localhost,127.0.0.1,::1,.local"`. httpx 0.28.1 derives its bypass mounts only from that `no` entry (`httpx/_utils.py:47`), so the child installs an HTTP and an HTTPS proxy mount for a loopback URL and no bypass, sends the request to the proxy at `127.0.0.1:7897`, and receives the cached empty `403`.

`prove-extraction-failure.mts` and its log `extraction-failure-diagnosis.log`, both recorded by a sibling Task 1 session in this evidence directory, trace the same chain end to end and show that the obligation is observable on this host without escalation. Step 1 runs the installed sidecar with the environment `src/sidecar.ts:231-237` builds: exit 1, `status: "uncertain"`, `completedChunks: 0`, `tokensUsed: 0`, zero recorded requests. Step 2 shows the child's own client: `defaultHttpxResponse` is the `403` with an empty body and `defaultHttpxJsonDecodeError` is `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`, while the same request with `trust_env=False` reaches the fixture and returns `200`. Step 3 re-runs the sidecar with `NO_PROXY=127.0.0.1,localhost` in the child environment alone and the approved-extraction path completes: exit 0, `status: "completed"`, `completedChunks: 9`, `tokensUsed: 468`, and 9 recorded provider requests.

**Named remediation item — the knowledge child receives no resolved proxy bypass.** Give the knowledge child the same resolved proxy environment every other harness child receives, so a system proxy cannot capture its loopback traffic. This is a product defect, not only a local condition: any user behind a system proxy reaches the same `403`, and the same missing bypass would refuse a model endpoint on loopback, such as a locally hosted OpenAI-compatible server. The template fix already exists in `packages/util/http-proxy/src/install.ts:262-279` and `packages/subprocess/subprocess-local/src/spawn.ts:44-46`: build the child environment through `scrubbedParentEnv()` and overlay `proxyEnvironmentForChild()`, the way `packages/subprocess/subprocess/src/index.ts:66-80` does, instead of tombstoning every proxy name. This audit does not implement it; it names it for Task 2 or a standalone scoped fix.

The consequence for this ledger is that the approved-extraction obligation is environment-blocked in the default child environment, completes under an explicit loopback bypass, and carries a named product co-cause. The row closes for baseline acceptance by re-running the same controls after the child receives the resolved bypass, without host escalation. The `ingest-failed` message the harness surfaces is the child's own error text, so the failure is already diagnosable from the harness log.

## 100 MiB ceiling recommendation

**Recommendation: do not adopt the 100 MiB library upload ceiling yet.** Keep `DEFAULT_MAX_INGEST_BYTES` at 20 MiB, and land Task 2's `File.slice()` streaming before any higher default is published.

The measured evidence supports the refusal from three directions. The whole-file path peaks at 808.8 MiB process RSS for a 100 MiB file, about eight times the payload, and that figure excludes the WebView and the renderer process. A 100 MiB upload costs 640 serial chunk calls and 139.8 MB of base64 on the wire, 4/3 of the file, before conversion begins. And the current admission cap would refuse such an upload anyway at chunk 128, so raising the ceiling without the streaming change would only let a doomed upload run further before failing.

Memory and transport are the plan's stated pass conditions. Transport is now measured in Node: `transport-measurements.log` records a 100 MiB upload over the desktop RPC path at 14.86 MiB/s with a 200 MiB RSS delta, and cancellation and cold restart have their own cases in the same log. WebView peak memory and renderer behaviour remain unmeasured, because they need the browser harness. The two measurements also differ in method — this audit's table materializes the whole encoded payload before the first call, while the transport run reports per-stage timings — so neither number substitutes for the other. The conversion dimension is measured and safe as it stands: the 50 MiB converted-output cap and the 8 MiB DOCX XML-entry cap both refuse visibly at the boundary and one byte beyond, with no silent clipping.

Task 2 should therefore be authorized with these measurements as its baseline, and the ceiling decision deferred until Task 2 publishes WebView numbers for sizes up to 100 MiB; the Node transport number it needs already exists in `transport-measurements.log`.
