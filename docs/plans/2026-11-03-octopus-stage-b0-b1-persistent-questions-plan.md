# Stage B0/B1 Persistent Questions Implementation Plan

**Goal:** Add structured, expiring questions to existing sessions, with desktop answers admitted through the normal Session prompt path and no second answer-delivery engine.

**Architecture:** A fork-owned `session-decisions` plugin provides question state, a model tool, a local Remote service, and client cards/badges. A single-record aggregate owns lifecycle and indexing; the Session log owns admitted answers. B0 verifies producer ordering and PTC coverage before B1 implementation. Feishu receipt delivery belongs to the separate B2 plan.

**Tech Stack:** Cordis, storage-domain, TypeScript, React, Typert remotes, existing Session controller, injected clock, Vitest, and Host-backed recorded Sessions.

**Execution status:** B0 source/design exit is independently reviewed READY FOR B1 CODE, 9/10. B1 implementation is active: foundation checks pass, while Host tools/preset and Client UI are in progress. Full feature, actual Host recovery, and installed acceptance remain open. See the [roadmap checkpoint](2026-11-03-octopus-implementation-roadmap.md#current-execution-evidence) and [final B0 review](../../.plans/octopus-implementation/orchestration/cursor-b0-final-review.md), including its four Suggested implementation obligations.

## Summary

The [roadmap](2026-11-03-octopus-implementation-roadmap.md) fixes two planning choices: authenticated answers retain full existing human-turn authority, and desktop answering stays thin while Feishu reuses its existing receipts. This plan audits those choices and delivers a local question card, session badge, expiry, safe refusal, and restart reconstruction. It adds no outer Task, Attempt, dependency scheduler, new task board, or background prompt-replay queue.

B0 itself produces evidence documents and runs existing checks; creating the feature package/tests starts B1. The written artifacts pin: the helper/cast human-source consumers the direct search missed (`tool-skill` gesture activation, session-reference expansion), a server-composed answer text (`Answer to question <uuid>: option <n>`) whose UUID decision-ID alphabet cannot match skill-gesture or session-mention scanners, and post-compaction context retrieval through a specified read-only `read_persistent_question` tool.

1. Search current consumers of `source.kind === 'user'` and equivalent human-source checks; record the actual set, not the historical approximate count. Trace Goal, job wake budgets, UI source labels, and any other discovered consumer to its executing owner.
2. State the authority consequence for each producer. Desktop answers and verified Feishu answers are real human input; event bookkeeping, timer expiry, and retry are not. A persisted original human command is not a new grant on each recovery.
3. Pin the accepted Goal choice: preserve current full-human authority, with no upstream tool-goal patch. The service disarms activation and never resumes it itself, but the model may resume an active-but-disarmed Goal in the answer turn. A Goal whose phase is actually paused still rejects model resume (`GOAL_TOOL_RESUME_PAUSED`). Use state-derived copy such as “自动续跑已停止，回答后可能继续”, not a mandatory-manual-resume promise. Test both phase cases.
4. Confirm normal desktop submission reaches `sessionController.prompt()`, `SessionCommandController.prompt()`, explicit human source creation, and `hasPromptRequest()` duplicate recognition. Trace both restored inbox entries and entered `user/message` events after cold restore; a warm-session check is insufficient. B1 must add a real persistence/restart duplicate-request test before claiming single admission. Always pass `mode: queue`; never use steer for a decision answer. Reuse the public path, not a copied prompt implementation or a delivery pump.
5. Limit the initial tool to composed root conversations, native tool calls, and no active owned jobs or delegated work. Ordinary assistants lacking the service simply retain ordinary chat questions. Define the reason and scope of each restriction.
6. Freeze browser-safe request/response fields before scaffolding. A question answer identifies decision ID, expected revision, choice/text, and one normal prompt request ID. Untrusted browser identity claims never establish the human actor.

**B0 exit evidence:** A reviewed source matrix accepts the existing full-human semantics and identifies every changed persisted type, if any. If the audited consequences require narrower authority, revise the design here rather than implementing a different meaning under `kind: user`.

## B0.2: Prove the concrete input and tool guards

**Inspect:** `packages/core/agent-loop/src/inbox.ts`, `packages/core/agent/src/runtime-types.ts`, `packages/core/tools/src/{index,ptc}.ts`, `packages/jobs/tool-jobs/README.md`, and Team/Schedule source owners.

**Specify B1 tests:** `packages/experimental/session-decisions/tests/input-ordering.spec.ts` and `tool.spec.ts`; document their cases in B0 evidence. Do not scaffold B1 code to perform this source audit. Existing core regression homes, only if an actual defect is demonstrated, are `packages/core/tools/tests/{scoped,ptc,execution-mode}.spec.ts` and the affected agent-loop tests. The written `guard-and-queue-oracles.md` artifact pins the deny-all-while-armed producing-step guard, event-observed identity, and matching step/end or turn/end reset, and the durable per-event handling of queue edits, removals, promotions, and clears — including the `withdrawn` admission-index value that blocks re-admitting a user-removed answer.

1. Use synchronous `agent/inbox/inserted` to increment an in-memory context generation and mark a pending question dirty. Do not perform awaited storage work in that synchronous callback. Enqueue durable invalidation on the service's serialized write queue.
2. Validate revision, expiry and choice in the answer Remote before calling `prompt()`. Once that call accepts the human input, always deliver it. If context changes afterward, supersede the question/index and let the model receive the answer as ordinary human text for revalidation. Do not filter messages or reject a step in `agent/pre-step`; an omitted message would never be logged despite prior `accepted: true`. The feature needs no pre-step input-rewriting gate.
3. Use an exclusive question tool and a scoped monotonic `tools.guard()` denial for leftover calls from the step that saved the question. Use `tools/pre-execute` for awaited tool admission and delegate when unaffected. The guard must survive another listener returning allow, but must not deny tools in a later human interaction. Reset at matching producing step/turn settlement or context disposal; there is no claim reset, because claims occur in the following pre-step. Cache positions through session/event rather than deprecated Session log readers. Insertion supersedes the question. Queue correlated answers so their new turn follows old-turn closure. Specify the producing-step identity and late-call checks without inventing a `ToolExecution.step` field.
4. Trace PTC `tool/ptc-dispatch-start` through `scheduler.prepare()` into the shared pre-execute/guard path. Test denial of a later same-step root run_code before its program starts; separately verify generic nested preparation and nested-question refusal in enabled both mode. A logged PTC dispatch start alone is not execution evidence.
5. First-release composition: use the feature-owned persistent-questions preset specified in B0 composition.md: restate standard roster, add the scoped ./tools consumer and explicitly pin native presentation. Keep default standard unchanged. Shipped PTC omits the consumer; user-edited PTC retaining it explicitly accepts SDK advertising plus nested-question refusal. In explicitly enabled both mode, reject persistent question creation from inside PTC programs with `DECISION_PTC_UNSUPPORTED`; ask in chat instead. A parent program can continue non-tool code after a nested tool returns, so hook coverage alone does not establish safe program termination. Keep this restriction unless a separately tested cancellation design closes that gap.
6. Trace every external producer: desktop prompt, authenticated IM chat for its own session, Schedule, Team mail, background completion, and Goal continuation. Specify tests for question supersession only. An exact correlated answer must not supersede itself; a non-correlated human steering message must supersede the question and be usable, with tools available, when claimed.
7. Specify barrier tests around question save, concurrent ordinary input, answer validation, Session admission, and turn closure. Include queue-mode answers before turn close, ordinary human steering, context changing after acceptance, and no-deadlock assertions. Already accepted human input must appear in the Session transcript even when its question is superseded.

**Required negative outcomes:** `DECISION_BUSY_OWNED_WORK`, `DECISION_PTC_UNSUPPORTED`, `DECISION_STALE_CONTEXT`, and `DECISION_CONFLICT` are proposed new feature errors, not existing Team error codes. Busy/PTC errors tell the model: “Ask the user in ordinary chat instead, or retry after owned work has settled. Do not stop or replace teammates.” Those failures must not save a question, send a notification, or leave Goal newly disarmed.

**B1 verification command, after B0 review and test creation:** `pnpm exec vitest run packages/experimental/session-decisions/tests/admission.spec.ts packages/experimental/session-decisions/tests/input-ordering.spec.ts packages/experimental/session-decisions/tests/tool.spec.ts`. **Expected during B1:** The implemented guards and delivery paths pass the specified adversarial cases. B0 exit evidence identifies current owners, exact test oracles and unresolved gaps; it does not claim those not-yet-created tests passed. Source inspection must settle admission behavior before B1 code.

1. Finalize one decision record with identity, revision, session/context references, question/choices, expiry, lifecycle state, optional answer request-ID pointer, and optional notification references. The Session's durable inbox/entered human message is the admitted-answer authority. Do not persist a second authoritative answer body or background continuation queue.
2. Allocate a normal prompt request ID once per desktop submission. Save an indexing reservation, invoke the existing prompt path, flush using the existing Session facilities, then update the index. A lost response is inspected against that request ID using existing Session readers; no timer retries desktop prompts automatically. If evidence is ambiguous, show unresolved status and require explicit user action.
3. Serialize answer validation, expiry, pause/cancel, and question supersession. Define which operations win before prompt admission. After `prompt()` accepts, later supersession must not retract or filter that human input. Requests with the same ID and payload return the existing outcome; same ID with conflicting content rejects. Keep only the digest/pointer needed for conflict checking outside the Session answer body.
4. Specify supported aggregate format revisions, owner-run backups/conversion, incompatible-record failure, and domain-version conversion before open. Include deletion and deduplication retention rules. No cross-record or SQLite-to-Session transaction is claimed.
5. Confirm a Host-capable recorded flow launches via `dsh --profile web` and the real Session controller/persistence. Existing headless Team replay is not sufficient. Identify the exact browser snapshot/scaffold owners through the current runner and record them before changing the harness.
6. Freeze default question lifetime at 24 hours and closed-record retention at 30 days as proposed validated configuration. Use persisted UTC expiry, injected wall time and monotonic delay scheduling; never prune live or unresolved answer/callback evidence merely to meet retention. Cap stored records and refuse creation when safe retention cannot free capacity.

**B0 completion:** Authority and Goal choice, queue-only answers, no post-admission filtering, producing-step guard mapping, PTC source evidence, answer ownership, cold-restore duplicate test requirements, persistence conversion, client extension slots, and Host-test composition are concrete and reviewed.
