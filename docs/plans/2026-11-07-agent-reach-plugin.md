# Agent-Reach Plugin Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Ship the lightweight Agent-Reach plugin enabled in the Octopus DSH desktop distribution, and guide users through installing only the missing dependencies when they first use a platform action.

**Architecture:** One seeded Cordis bundle provides a managed Agent-Reach execution service, three read-only tools and one separate setup tool whose default availability and approval semantics follow Section 6. Dependency installation is lazy, approved and scoped to a qualified action/backend; the executor invokes the resulting Python CLI with validated argv through DSH subprocess services. A small Client contribution presents setup/result status using existing UI components; no media agent, platform-adapter fork or MCP server is introduced.

**Tech Stack:** TypeScript, Cordis, existing DSH tools/subprocess/presentation APIs, lazily installed or compatible existing Agent-Reach Python CLI, existing approval and desktop seed mechanisms, Vitest and recorded DSH sessions.

**Status:** Implementation is authorized by the user. The default-enabled narrow setup tool always requests interactive approval through the existing approval service, including in full-access sessions. Publication remains separate. Acceptance evidence is tracked under `.plans/agent-reach-orchestration/`.

## 1. Product scope

A fresh Octopus DSH desktop installation contains and enables the lightweight plugin through the fork-owned desktop profile seed. The four tools are enabled; the mutating setup tool always requires an interactive grant. Users do not install the plugin separately. Disabling/removing it remains available in the existing Plugins page, and refresh must preserve that choice. CLI/Web/Linux profiles can still install its tarball explicitly rather than changing every upstream profile. The plugin adds capabilities to existing conversations and Team members that inherit that profile's tools; it does not create or select another agent preset. Existing tool-access policies still apply.

The first release delivers channel discovery, local status, bounded read-only platform queries and a separate first-use dependency setup tool, with the approval behavior in Section 6. The catalog describes all channels from the qualified upstream release. Enabled channels are deployment configuration, initially Bilibili, YouTube and V2EX; users can enable additional nonexperimental channels after setup. Browser/session side effects require explicit opt-in per action/backend, including actions in otherwise enabled native channels. Enabling Bilibili does not enable its subtitle action by default. Experimental channels remain disabled by default and must be labelled when enabled. Enabling a channel is not a claim that it has passed live acceptance.

The default DMG/EXE includes only the plugin code, locale/presentation assets and qualified dependency manifests. It adds no Python runtime, Agent-Reach environment, browser, platform executable, FFmpeg, eager network setup or new media agent. The plugin may use existing desktop tool rows and approval UI; it adds no marketplace or dedicated settings page. Boot works offline with dependencies absent, and no service is started merely because the plugin is seeded. Agent-Reach's optional browser backend may run its existing Bridge/browser after an action/backend with browser/session effects is explicitly permitted; public CLI-only channels require no new listening port from this plugin.

Posting, commenting, private messaging, arbitrary commands, transcription/audio uploads, arbitrary dependency-management commands and account-management tools are excluded from the first release. Existing DSH web tools remain preferred for ordinary public web access. No changes are planned to the Linux operations broker or WeChat worker.

## 2. Installation and ownership

Source package: `packages/experimental/agent-reach`, named `@deepseek-ai/dsh-experimental-agent-reach`. Public publication follows this fork's existing rescope process; the exact public package name must be verified in the packed artifact before documenting a registry install. An independently installable tarball remains a build artifact, but first acceptance requires the actual seeded desktop DMG and Windows EXE behavior as well. Registry publication requires a separate explicit request.

The package declares `dsh.bundle.patch`, includes compiled Host code and its patch, and declares all runtime dependencies required outside a source checkout. It has no package bin or npm lifecycle installer. It supplies Host and Client leaf compiler programs, a solution-only root, `dsh.client.platform: web` and a compiled `./client` export, as required by the existing desktop seeder. The Client owns lightweight setup/result presenters and locale-owned copy, not a placeholder no-op added only to bypass validation. The bundle mounts its execution service and tool consumer from one entry in the same package, with a shared disposal lifetime. The tool consumer registers synchronously; missing Python/Agent-Reach does not prevent DSH from booting.

Choose installation option (a): plugin-owned, fully hash-locked environments outside `~/.agent-reach`. The default runtime root is `<DSH_HOME>/runtimes/agent-reach/releases/<lock-id>/`, with separate core and native-tool venvs and an owner record. A compatible external Agent-Reach installation is used only through an explicit absolute administrator override; do not discover or select one from the desktop's ambient PATH. The repository's existing warning that the similarly named PyPI package is not this project must remain visible in setup instructions. Do not copy an unpinned latest-source installation command into the guide. Record the reviewed upstream source revision, version, catalog and artifact/source digest in `runtime-contract.json` during implementation; the initial candidate is the reviewed local checkout at `/Users/apple/Skill_hub_knowledge/skills/Agent-Reach`, which declares version 1.6.1. Capture and verify its exact source revision before implementation rather than treating the version string as an immutable tag. A version string alone does not attest to source identity.

Prefer the qualified plugin-owned Agent-Reach environment and DSH's bundled Node. External runtime/tool reuse requires an explicit administrator override and qualification; never replace the user's Node, Python, browser, FFmpeg or accounts. Missing dependencies return a structured NEED_SETUP result with the exact action/backend setup request. The model may then invoke the separate `reach_setup` tool, which computes a fixed installation plan and must use the default/approval rule selected in Section 6 before downloading or executing anything. The cited `approveEscalation` pattern auto-grants in an effective danger-full-access session; it does not guarantee a prompt. Approval rejection, cancellation or no available approval path leaves setup incomplete; it must not become a manual-only assumption hidden behind a success message. Queries and startup never invoke setup/add/update/login/remove/uninstall. The plugin does not install upstream skill links into other agents. Manual setup remains an alternative, not the default user journey.

On a personal desktop, Agent-Reach account/session state follows its existing OS-user layout; privately installing its executable does not create isolated upstream account state. Two DSH profiles using the same OS account may share that state: do not describe this as profile or tenant isolation. A Linux deployment uses its own unprivileged service account and separately provisioned login state; it cannot reuse a Mac browser implicitly.

## 3. First-use experience, tools and configuration

| Tool | Input | Behavior |
|---|---|---|
| `reach_channels` | none | Return the qualified channel/action catalog, parameter metadata, action/backend side effects, effective enablement and prerequisites; do not install or log in |
| `reach_status` | optional channel | Read version and local doctor state; distinguish unavailable, disabled, unsupported, unverified, recently checked, login-required and cooldown; never claim to have run a fresh probe |
| `reach_query` | channel, action, params, optional declared backend | Execute one allowed read operation; return content, result scope, attempt history and explicit completeness limits, or a structured setup request |
| `reach_setup` | qualified channel/action, optional declared backend | Inspect missing dependencies, present a frozen installation plan, obtain existing DSH policy approval and install only that plan; no arbitrary commands/packages/URLs |

The ordinary flow is request → dependency/session-policy inspection → missing-dependency explanation → `reach_setup` approval and progress → version/action verification → a fresh `reach_query` call. No setup is attempted if prerequisites already work. Do not replay an expired or cancelled query automatically after a long installation, or loop through setup retries. A session-forbidden route remains rejected before query subprocess probing even when its dependencies are installed; dependency approval never grants cookie/session access.

`reach_query` validates against the checked-in qualified catalog, not arbitrary command names supplied by the model or runtime. Reject unknown channels/actions/parameters, disabled channels, management commands and transcription before spawning. Validate integer ranges and URL fields. A backend must be declared for that action. Build named flags before a `--` separator and positional values afterwards; never pass a model-provided argv array or shell string. Cover queries that look like flags and URLs containing metacharacters.

Proposed validated configuration fields and initial defaults:

| Field | Initial value | Purpose |
|---|---|---|
| `runtimeOverride` | unset | Optional explicit absolute administrator-selected Agent-Reach launcher; otherwise use only the qualified plugin-owned runtime, with no ambient PATH discovery |
| `enabledChannels` | bilibili, youtube, v2ex | Explicit channel selection |
| `sessionAccessRoutes` | empty list | Exact channel/action/backend tuples permitted to discover browsers, import cookies, write native credentials or launch browsers after explicit setup |
| `allowExperimentalChannels` | false | Additional explicit permission for experimental channels |
| `setupTimeoutMs` | 900000 | Overall bounded download/install deadline, separate from a query |
| `queryTimeoutMs` | 90000 | Overall deadline including queue and browser startup |
| `maxConcurrentQueries` | 4 | Limit across callers of this plugin instance |
| `maxStdoutBytes` | 1048576 | Bound complete CLI JSON before parsing |
| `maxStderrBytes` | 32768 | Bound private diagnostic capture |
| `maxOutputChars` | 24000 | Bound model-visible extracted content |
| `maxItems` | 20 | Bound requested/returned items where supported |
| `terminateGraceMs` | 5000 | Managed subprocess teardown allowance |

The qualified catalog records side effects for every action/backend: connected-browser discovery, cookie import, native credential writes and browser launch, separately from reading an explicitly provisioned native login. Compute permission over every backend reachable through the selected route and its fallback. With the default empty `sessionAccessRoutes`, reject any route capable of the classified effects before version probing or spawning any subprocess. Opt-in names an exact channel/action/backend tuple, such as Bilibili/subtitle/bili-cli; it grants no other action or backend. Reject wildcards and unknown tuples in configuration. Every reachable effectful fallback needs its own permitted tuple. An explicit backend may narrow the route only when qualification establishes that no automatic fallback reaches a forbidden backend. Unknown effect classifications fail closed.

In the candidate upstream, `bilibili subtitle` calls `_reuse_subtitle_login()` and `reuse_browser_session()` before `_bili_json()`. That path can discover connected-browser cookies and write a bili-cli credential without launching a browser. Classify it as browser discovery, cookie import and native credential write, and block it under the default configuration even when Bilibili is enabled. A provisioned native login alone does not remove this gate. A future native-only path requires a qualified upstream mechanism that prevents automatic import; do not infer one from login presence, tool name or a modified local state record.

Declare accepted ranges and reject invalid configuration at load. These values are product configuration, not hidden constants. Keep upstream's own account/site pacing; do not attempt to evade it through alternate backends or accounts. The outer deadline does not pause when upstream pauses its action clock.

## 4. Execution, results and login behavior

Resolve the default Agent-Reach entry point from the plugin-owned installation record, not Finder/Terminal PATH. Prepend the qualified core/tool venv bin directories and bundled Node directory to a controlled spawn PATH; on Windows use the corresponding Scripts/executable directories. This is the selected upstream integration mechanism: `tools.resolve()` can discover plugin-owned commands through its PATH fallback, and offline present/doctor checks see the same environment as queries. Never write binaries, venvs, installer receipts or fabricated ownership records into `~/.agent-reach/tools`, and never run `agent-reach add` as an install recipe.

Upstream private tools take precedence over PATH. Before doctor or backend execution, use the pinned runtime's read-only resolver to inspect actual tool paths without executing those tool binaries. If an existing `~/.agent-reach/tools` command shadows the qualified command, return an explicit conflict/NEED_SETUP diagnostic; do not silently use it, remove it, alter its ledger or claim that PATH prepending overrides it. An administrator can resolve the conflict manually. `runtimeOverride` selects a different CLI only; it does not waive backend path/digest qualification or create an implicit external-tool override. Test both a clean upstream tool tree and an unqualified shadowing copy. This preserves the user's upstream state while keeping the selected executable deterministic.

The service resolves an execution request to a complete spawn specification: executable, fixed argv, safe working directory, bounded stdout/stderr, environment, cancellation and teardown. Use `ctx.subprocess`; do not introduce raw child_process ownership or an independent Node launcher. Disable upstream background update notifications for calls. Keep its existing user-state lookup; do not invent an unsupported Agent-Reach state-directory flag. Forward no ambient DSH API secrets. Task 2 must qualify transient-backend containment before any channel can be accepted, including CLI-only channels.

A stdout collector that retains only the tail is insufficient for JSON. Use a bounded complete-stream reader; on byte overflow, abort and reject rather than parsing a truncated tail. Expect exactly one JSON document. Validate command-specific schema versions and fields: channels/doctor responses differ from query envelopes. Treat nonzero exit with a valid upstream error envelope as a structured domain failure; malformed output or failed process ownership is an adapter error. Do not infer success from exit zero alone.

A valid query preserves channel, action, backend, item URLs/authors/dates/text, attempt history, public/native access and completeness flags. Omit uncontrolled raw payloads from model output. Truncate text deterministically and mark it; do not call truncated content complete. Render external text as untrusted data using existing DSH mechanisms, and redact credentials and secret URL values from upstream output before presentation or session logging. Do not retain cookie-bearing raw stdout as a deliverable. User messages and model tool arguments already belong to the normal Session log: never request credentials as query parameters, and do not promise retroactive redaction of secrets supplied in those inputs.

Design Host call/result presenters before tool implementation. Use pure presenters and existing tool rows, with durable metadata for channel/action/backend, access scope, item count, truncation, elapsed time and error code. A lightweight Client presenter renders these same durable facts plus setup status in existing tool rows; its copy uses typed locale dictionaries. It does not invent a separate task panel or custom approval protocol. Missing content must remain unknown: a public snippet is not a full post, loaded comments are not all comments, and a subtitle-track list is not subtitle text. Normal tool calls/results provide the durable model-visible record; add no Session event for query results. Setup owns a small versioned private installation record; review its durable types and upgrade/refusal behavior without changing released Session formats.

Do not retry queries in the adapter. Preserve NEED_LOGIN, RATE_LIMITED, PLATFORM_BLOCKED and BUSY as actionable states; generic network failures must not be relabelled as login failures. Upstream may perform its own declared fallback. Cancellation, timeout and plugin disposal must terminate owned transient query processes and await managed-range quiescence. The candidate upstream `runtime/run.py` launches ordinary backend commands with `start_new_session=True` on POSIX unless `REACH_API_SUPERVISED=1`. DSH's macOS provider owns a process group, so terminating only the top-level CLI can leave a detached bili/yt-dlp backend alive. Evaluate the pinned upstream supervised mode in Task 2, including propagation to nested transient commands and its timeout branch, which kills only the direct subprocess. Treat the environment flag as a candidate containment mechanism, not evidence that containment works. The adapter must supervise the whole transient range and clean it up on error and timeout, including when the CLI exits first. If the qualified mode cannot satisfy this behavior, block affected routes/platforms rather than claiming cleanup or shipping unqualified CLI-only queries.

Shared upstream browser/Bridge processes are user-owned resources, not query descendants to kill indiscriminately. Qualify their survival separately from transient-backend termination; a fix that preserves a browser by allowing transient query workers to escape is not acceptable. Distinguish a pre-existing shared process from one launched by the query. A query-started browser/Bridge needs a qualified persistent owner or explicit external startup; do not relabel it as pre-existing to exclude it from teardown.

Browser/session opt-in must explain each permitted route's behavior: first use may copy this site's cookies into a dedicated browser, or, for native Bilibili subtitles, write a bili-cli credential from the connected-browser cookies; browser cold startup may prepare missing assets. The plugin does not replace or harden that upstream behavior. Only enable this mode after explicit user setup; do not promise that executing upstream code cannot write files or acquire assets. An unavailable session returns guidance for user-completed login; the plugin does not open login windows or collect passwords in chat.
