# 桌面发布准备与发布

[English](desktop-releases.md) | 中文

桌面构建默认为 `internal`：未签名的 Windows 安装程序以及临时签名、未经公证的 macOS 镜像仅用于受控测试。将 `DSH_DESKTOP_ARTIFACT_DIR` 指向空的候选目录，避免替换已交付的安装程序。每次构建都会在外部生成 `.release.json`，记录已测试的源码、运行时与外壳版本、目标平台、适用的 CI 运行及尝试编号、安装载荷摘要，以及最终产物大小和 SHA-256。本机构建不能冒充通过公共发布资格核验的 CI 产物。公共 DMG 只包含正常的拖放安装说明；清除隔离属性的助手和内部绕过说明仅保留在内部镜像中。公共模式签名为 Node 开放 V8 JIT 和用户选择的原生插件加载权限；这些授权应用于 Node 可执行文件，不应用于应用外壳。

打包要求同一 HEAD 已完成的根构建记录，以及未改变的已构建 Client 摘要。外壳 Vite 构建、安装程序构建信息和发布清单读取该持久化发布标识。内部构建允许修改过的检出目录，并在构建信息与发布清单中披露来自完成记录的 `sourceState.modifiedAtBuild`，以及来自当前 Git 状态的 `modifiedAtPackaging`。公共构建拒绝任一标记为真。缺少 `sourceState` 的旧清单无法确认源码状态，必须重新生成清单并核验产物；缺少字段不代表源码干净。

外壳版本来自 `apps/desktop/src-tauri/tauri.conf.json`，独立于 JavaScript 包版本与 Harness 运行时版本。应与已安装可执行文件的版本元数据核对。

安装载荷摘要仅在相对符号链接解析到实际载荷目录内部时，计入链接名称及其目标原文；绝对路径、越界、损坏和循环链接均被拒绝。

## 准备候选产物

1. 构建工作区和冻结的知识库辅助进程，然后在 Windows 上运行 `node scripts/build-exe.mjs`，或在 macOS 上运行 `bash scripts/build-dmg.sh --arch arm64`。Windows 自定义模板基于 Tauri CLI 2.11.4；模板头部记录了上游模板摘要。更新模板必须保留 WebView 安装、注册表、快捷方式、文件关联和卸载程序行为。
2. 对临时安装或只读挂载的 DMG 执行安装后验证。Windows 工作流要求安装程序退出码为零、安装后就绪检查、知识库 Host 检查，以及原生 `scripts/tests/desktop-installer-upgrade.ps1` 检查。该脚本重新编译 Tauri 生成的完整 NSIS 脚本并实际执行安装和卸载，同时编译事务样例，覆盖 A 到 B 升级、拒绝外来目录、所属暂存与备份清理、临时与永久辅助进程锁、发布失败、回滚失败、中断恢复、重新安装，以及辅助进程重启。源码测试不能证明原生升级验收通过。
3. 公共模式需设置 `DSH_DESKTOP_BUILD_MODE=public`。Windows 需要 `DSH_WINDOWS_CERTIFICATE_THUMBPRINT` 对应的私钥存在于当前用户证书存储中，并且 `DSH_WINDOWS_PUBLISHER` 与受信证书主题一致。macOS 需要 `DSH_MAC_SIGNING_IDENTITY`、`DSH_MAC_TEAM_ID`，以及钥匙串中已认证的 `DSH_NOTARY_PROFILE`。仅检查配置的预检在昂贵构建前核验模式、目标、公共设置名称及 CI 密钥是否存在的布尔值，不导入密钥。原生凭据核验在导入后、签名前执行；CI macOS 流程先完成组装、临时签名与捆绑程序就绪检查，再导入凭据。公共 macOS 构建必须先运行 `--prepare-only`，再导入凭据，最后运行 `--sign-prepared`；未分阶段的公共构建命令会被拒绝。最终资格核验调用原生 Authenticode 或 Developer ID、操作系统信任、公证和装订检查；清单中的声明不能替代这些检查。

CI 公共构建引用 `desktop-signing` 环境；公共使用前，仓库管理员必须配置必需审核人、部署分支限制及签名密钥。仅在 YAML 中命名环境不会配置这些保护。Windows 使用 `DSH_WINDOWS_CERTIFICATE_PASSWORD` 导入 `DSH_WINDOWS_CERTIFICATE_BASE64`（PFX）；配置的指纹必须指向其私钥。macOS 在尚未导入签名密钥时完成依赖安装、Tauri 编译、插件组装与辅助进程冻结，随后使用 `DSH_MAC_CERTIFICATE_PASSWORD` 将 `DSH_MAC_CERTIFICATE_BASE64`（PKCS#12）以不可导出、可信应用 ACL 指定为 `/usr/bin/codesign` 的密钥导入临时钥匙串（同时保留 macOS codesign 要求的 `apple:` 分区），并将 `DSH_MAC_NOTARY_KEY_BASE64`（P8）、`DSH_MAC_NOTARY_KEY_ID` 和 `DSH_MAC_NOTARY_ISSUER_ID` 提供的 App Store Connect API 凭据存入配置的公证凭据名称。无签名组装与签名是同一运行器上的独立阶段；准备阶段只有在捆绑程序检查通过后，才保存应用摘要、架构、模式及就绪结果。签名阶段拒绝内容变化或缺少就绪结果的旧准备记录，且不运行捆绑的伴随进程或 Python 运行时。签名密钥导入期间不执行包管理器命令，后续挂载冒烟检查前执行清理，失败时也会清理。强化运行时应用签名授予麦克风输入权限；JIT 和原生库权限仅保留给 Node。macOS 公共签名根据文件头识别所有 Mach-O 文件，包括无扩展名的辅助程序和原生库，在封装应用签名前逐一签名原生文件和嵌套代码包，并核验团队标识、强化运行时及安全时间戳。

## 恢复中断的 Windows 升级

安装程序先在安装目录旁暂存完整候选载荷，再替换现有安装。它对已安装的主程序、Node 辅助进程和知识库辅助进程执行独占访问探测，仅对访问、共享或锁冲突重试，每个替换步骤最多十秒。它不会终止 Node 进程。替换失败会保留旧载荷，并报告暂存、备份和事务日志路径。恢复时先核验事务日志的目标、相邻目录命名及重解析点限制，再移动文件。替换前恢复仅清理带有标记、令牌匹配且无重解析点的暂存目录，随后清除日志；无标记或状态不明确的暂存目录会保留日志供检查。当前安装缺失时可恢复备份。受信的 Windows PowerShell 助手在发布前为完整的暂存文件和目录清单封存摘要；状态不明确的 `replacing` 恢复仅在目标仍匹配绑定事务标识的摘要时才会确认发布。持久化状态为 `committed` 的恢复接受安装程序身份，即使之后发生运行时写入，也会清除日志，并将备份清理失败视为非致命错误。目标被修改或状态不明确时，保留两个目录及日志供操作人员检查。

非空目标目录必须具有安装程序身份标记，或具有完全匹配的旧版 `InstallLocation`、`Publisher` 注册表值，以及预期的主程序、Node 和卸载程序。外来目录在任何移动前即被拒绝。升级成功后，仅清理内容未变且校验和一致的已封存备份；应用正常写入不会阻止后续升级。清理在删除前先移除备份的就绪标记；安装提交后，包括已提交状态恢复期间，清理失败不改变安装成功结果。修改过或内容未知的备份保留供检查，可能累积；未封存的旧版备份保留供操作人员检查。清理遗弃暂存目录要求匹配的事务标记和令牌，且不含重解析点。修改过或状态不明确的目录及其事务日志保留供恢复，并阻止反复替换。卸载仅移除原安装路径下声明的安装文件，保留无关个人文件。清理不会触碰用户主目录、知识库、原始文件、会话或凭据。

## 明确规划并发布

发布仅面向 `AlataChan/deepseek-harness`。规划前，需在已测试的确切提交上创建版本发布及标签 `desktop-v<version>`，并创建独立频道发布及标签 `desktop-channel-<channel>-<target>`。发布程序不会创建或移动标签。每个平台拥有独立的权威频道记录，因此发布 Windows 不会丢失 macOS 下载位置。这些记录用于下载，不会启用自动更新程序。

使用手动 `Desktop release publication` 工作流，首先选择 `operation=plan`，指定成功打包的确切运行编号、尝试编号、提交、产物名称及目标平台。只读作业在执行候选代码前，严格核验清单、指定执行、下载字节、归档中的生产者清单，以及原生安装程序或容器签名。随后仅安装到临时目录或只读挂载，对安装程序与冒烟检查进程清除环境中的凭据类变量，并验证安装载荷。独立的写入作业不执行候选代码；它要求只读作业成功，并接收不可变的已审计划。调用 `verify` 或 `publish` 前审查输出的计划 JSON；这两个操作要求提供审查过的原始 JSON。最后的写入程序在任何写入前，将交接文件字节与原始已审 JSON 输入比较，包括频道修订。发布会保留原计划而非重新生成；远端状态变更时拒绝执行，除非只读核验确认审查过的确切发布已经完整完成。`plan` 和 `verify` 不写入发布。即使旧清单声称通过，未签名的公共输入也会被拒绝。

来源资格核验仅接纳本分支仓库的 `master` 或 `release`，以及目标平台固定的 `desktop-windows.yml` 或 `desktop-macos.yml` 工作流。发布工作流本身也必须在这两个分支之一运行。启用发布前，应为 `desktop-public-release` 环境配置必需审核人、部署分支限制及其密钥。这两个发布环境属于外部前置条件，其保护不会由工作流文件自动建立。其 `DSH_DESKTOP_PUBLISH_TOKEN` 密钥需要访问本仓库发布资产及 Actions 证据；仅最后的发布步骤接收该密钥。此前步骤使用只读 GitHub 令牌。Actions 固定到不可变修订。功能分支仍可构建内部验证产物，但不能获得公共发布资格。

发布程序先上传不可变的带版本号二进制文件，再下载并比较大小和摘要，最后更新频道记录。相同对象会复用；冲突对象，以及 GitHub 状态不为 `uploaded` 的资产均被拒绝，即使上传返回 HTTP 成功。二进制上传或回读失败时，已上传的有效文件保留，可用同一计划继续。频道操作失败后，重跑前必须先核验；如果删除成功但替换失败，应针对观察到的缺失记录明确重新规划。发布工作流通过仓库级并发组串行执行受支持的写入。GitHub 发布资产替换不是原子比较交换：程序会在替换前后检查观察到的修订，但不支持绕过工作流手动写入频道，发生此类操作需人工协调恢复。

签名凭据、原生签名成功证据，以及原生 Windows 升级验收属于外部前置条件。缺少证据仍记为待验证；源码或样例测试不能赋予安装程序公共分发资格。
