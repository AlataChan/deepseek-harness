# Desktop release preparation and publication

English | [中文](desktop-releases.zh.md)

Desktop builds default to `internal`: unsigned Windows installers and ad-hoc-signed, unnotarized macOS images are for controlled testing. Set `DSH_DESKTOP_ARTIFACT_DIR` to an empty candidate directory to avoid replacing delivered installers. Every build writes an external `.release.json` containing the tested source, runtime and shell versions, target, CI run/attempt when present, installed payload digest, and final artifact size and SHA-256. A local build cannot qualify as a public CI artifact. Public DMGs contain normal drag-to-install instructions only; the quarantine-clearing helper and internal bypass instructions stay in internal images. Public Node signing permits V8 JIT and loading user-selected native plugins; those entitlements apply to the Node executable, not the application shell.

Packaging requires a completed root build from the same HEAD and unchanged built Client digests. The shell Vite build, installer build information, and release manifest read that persisted release identity. Internal builds allow a modified checkout and disclose `sourceState.modifiedAtBuild` from the completed record and `modifiedAtPackaging` from current Git state in build information and the release manifest. Public builds reject either flag. Older manifests without `sourceState` cannot establish source state and require fresh manifest and artifact qualification; absence never implies clean source.

The shell version comes from `apps/desktop/src-tauri/tauri.conf.json`, independently of the JavaScript package and Harness runtime versions. Verify it against the installed executable's version metadata.

The payload digest includes relative symlink names and literal targets only when they resolve inside the physical payload directory; absolute, escaping, broken and cyclic links are refused.

## Prepare a candidate

1. Build the workspace and frozen knowledge sidecar, then run `node scripts/build-exe.mjs` on Windows or `bash scripts/build-dmg.sh --arch arm64` on macOS. The Windows custom template is based on Tauri CLI 2.11.4; its upstream template digest is recorded in the template header. Template updates must preserve the WebView installation, registry, shortcut, association and uninstaller behavior.
2. Run installed verification against a disposable installation or read-only DMG mount. The Windows workflow requires a zero installer exit, installed readiness, knowledge Host checks, and the native `scripts/tests/desktop-installer-upgrade.ps1` controls. Those controls recompile the complete Tauri-generated NSIS script, execute its install and uninstall, and compile transaction fixtures covering A-to-B upgrades, foreign-directory refusal, owned-stage and backup cleanup, transient/permanent companion locks, failed publication, rollback failure, interrupted recovery, reinstall, and companion restart. Source tests do not establish native upgrade acceptance.
3. For public mode, set `DSH_DESKTOP_BUILD_MODE=public`. Windows requires `DSH_WINDOWS_CERTIFICATE_THUMBPRINT` with its private key in the current user's certificate store and `DSH_WINDOWS_PUBLISHER` matching the trusted certificate subject. macOS requires `DSH_MAC_SIGNING_IDENTITY`, `DSH_MAC_TEAM_ID`, and an authenticated `DSH_NOTARY_PROFILE` in the keychain. Configuration-only preflight checks mode, target, public setting names and CI secret-presence booleans before expensive builds without importing keys. Native credential verification runs after import and before signing; the CI macOS lane completes assembly, ad-hoc signing and bundled readiness before importing credentials. Public macOS builds require `--prepare-only` first, then credential import, then `--sign-prepared`; the unphased public command is refused. Final qualification invokes native Authenticode or Developer ID, OS trust, notarization and stapling checks; a manifest claim never substitutes for them.

CI public builds reference the `desktop-signing` environment; repository administrators must configure required reviewers, deployment branch restrictions, and the signing secrets before public use. Merely naming an environment in YAML does not configure those protections. Windows imports `DSH_WINDOWS_CERTIFICATE_BASE64` (PFX) using `DSH_WINDOWS_CERTIFICATE_PASSWORD`; the configured thumbprint must identify its private key. macOS completes dependency installation, Tauri compilation, plugin assembly, and sidecar freezing with no imported signing key, then imports `DSH_MAC_CERTIFICATE_BASE64` (PKCS#12) using `DSH_MAC_CERTIFICATE_PASSWORD` into a temporary keychain as a non-extractable key whose trusted-application ACL names `/usr/bin/codesign` (with the `apple:` partition required by macOS codesign), and stores the App Store Connect API credential from `DSH_MAC_NOTARY_KEY_BASE64` (P8), `DSH_MAC_NOTARY_KEY_ID`, and `DSH_MAC_NOTARY_ISSUER_ID` under the configured notary profile. Unsigned assembly and signing are separate phases on the same runner; preparation seals the application digest, architecture, mode and readiness result only after the bundled check succeeds. Signing refuses changed inputs and older preparation records without readiness. The signing phase does not execute the bundled companion or Python runtime. No package-manager command runs while the signing key is imported, and cleanup runs before the later mounted smoke check, after failures as well as successes. The hardened application signature grants microphone input; Node alone keeps the JIT and native-library entitlements. Public macOS signing discovers every Mach-O file by its header, including extensionless helpers and native libraries, signs native files and nested code bundles before the enclosing app, and checks its team, hardened runtime, and secure timestamp.

## Recover an interrupted Windows upgrade

The installer stages a complete candidate beside the installation before replacing it. It probes the installed main executable, Node companion and knowledge sidecar for exclusive access, then retries only access/sharing/lock violations for at most ten seconds per replacement step. It does not kill Node processes. Replacement failures preserve the previous payload and report the staging, backup and journal paths. Recovery validates the journal target, sibling names and reparse-point restrictions before moving files. Pre-move recovery removes only marked, token-matching staging without reparse points before clearing its journal; unmarked or ambiguous staging retains the journal for inspection. A missing live installation can restore its backup. A trusted Windows PowerShell helper seals the complete staged file/directory inventory before publication; ambiguous `replacing` recovery recognizes publication only when the destination still matches that token-bound inventory. Durable `committed` recovery accepts installer identity despite subsequent runtime writes, clears the journal and treats backup cleanup failure as nonfatal. Modified or ambiguous destinations retain both trees and the journal for operator inspection.

A nonempty target must have the installer identity marker, or have the exact legacy `InstallLocation` and `Publisher` registry values plus the expected main executable, Node and uninstaller. Foreign targets are refused before any move. Successful upgrades prune only unchanged, checksum-verified sealed backups; normal application writes do not prevent a later upgrade. Cleanup retires a backup's ready marker before deletion and remains nonfatal after installation commits, including during committed-state recovery. Modified or unknown backup contents are retained for inspection and can accumulate; a legacy unsealed backup remains for operator inspection. Abandoned staging cleanup requires the matching transaction marker and token with no reparse points. Modified or ambiguous trees and their journal remain for recovery and block repeated replacement attempts. Uninstall removes declared installed files at the original installation path and preserves unrelated personal files. Cleanup never touches user homes, libraries, originals, sessions or credentials.

## Plan and publish explicitly

Publication targets only `AlataChan/deepseek-harness`. Create the version release/tag `desktop-v<version>` at the exact tested commit and a dedicated channel release/tag `desktop-channel-<channel>-<target>` before planning. Publication never creates or moves tags. Each platform has its own authoritative channel record, so publishing Windows does not discard macOS destinations. These are download records; they do not enable an automatic updater.

Use the manual `Desktop release publication` workflow, initially with `operation=plan`, the exact successful packaging run ID/attempt/commit, its artifact name and target. A read-only job strictly validates the manifest, selected execution, downloaded bytes, archived producer manifest and native installer/container signature before any candidate code executes. It then installs only into a disposable directory or mounts read-only, scrubs credential-shaped environment variables from installer and smoke processes, and verifies installed payloads. A separate write job never executes candidate code; it requires the successful read-only job and immutable reviewed-plan handoff. Review the emitted plan JSON before invoking `verify` or `publish`; those operations require the exact reviewed JSON. The final writer compares the handoff bytes with the original reviewed JSON input, including the channel revision, before any write. Publication preserves that plan instead of regenerating it; changed remote state is refused unless read-only verification proves that the exact reviewed release is already fully published. `plan` and `verify` never write releases. Public unsigned inputs are refused even when an old manifest claims otherwise.

Source qualification admits only `master` or `release` on the fork and the target's fixed `desktop-windows.yml` or `desktop-macos.yml` workflow. Publication also requires its own workflow to run on one of those branches. Configure the `desktop-public-release` environment with required reviewers, deployment branch restrictions, and its secret before enabling publication. Both release environments are external prerequisites, not protections established by the workflow file. Its `DSH_DESKTOP_PUBLISH_TOKEN` secret needs access to this fork's release assets and Actions evidence; only the final publishing step receives it. Earlier steps use a read-only GitHub token. Actions are pinned to immutable revisions. Internal feature-branch builds remain available for verification but cannot qualify for public publication.

The publisher uploads immutable versioned binaries, downloads them to compare size and digest, then updates the channel record last. Identical objects are reused; conflicting objects and assets whose GitHub state is not `uploaded` are refused, even when an upload returned HTTP success. A failed binary upload/readback leaves valid uploaded assets intact and can resume with the same plan. A failed channel operation must be verified before rerunning; if deletion succeeded but replacement failed, explicitly re-plan against the observed missing record. The publication workflow serializes supported writers with one repository-wide concurrency group. GitHub release asset replacement is not atomic compare-and-swap: the publisher checks the observed revision before and after replacement, but out-of-band manual channel writes are unsupported and require operator reconciliation.

Signing credentials, positive native signing evidence, and native Windows upgrade acceptance are external prerequisites. Missing evidence stays pending; source or fixture tests do not qualify an installer for public distribution.
